# 알약 각인 인식 OCR 실험 정리

## 1\. 실험 목적

현재 알약 식별 웹 데모는 다음 흐름을 기준으로 구성되어 있습니다.

```text
사용자 이미지 업로드
→ RTMDet로 알약 위치 검출 및 1차 후보 예측
→ 검출된 알약 crop 생성
→ CNN으로 crop 이미지 재분류
→ RTMDet 후보 + CNN 후보 + API 정보로 최종 판단
```

이 구조에서 RTMDet과 CNN이 서로 다른 후보를 예측하거나, 두 모델이 모두 정답이 아닌 후보를 높은 confidence로 예측할 가능성이 있습니다.  
따라서 알약 표면의 각인을 OCR로 안정적으로 읽을 수 있다면, 낱알식별정보 API의 `PRINT\_FRONT`, `PRINT\_BACK` 정보와 비교하여 제3의 검증축으로 활용할 수 있다고 판단했습니다.

OCR의 목표는 단순히 각인 문자열을 출력하는 것이 아니라 다음과 같습니다.

```text
RTMDet/CNN 후보가 불일치하거나 불안정함
→ OCR로 각인 후보 추출
→ API 각인 정보와 비교
→ 실제 약품 후보를 보조적으로 추정
```

## 2\. EasyOCR 실험

초기에는 EasyOCR을 이용해 알약 각인 인식을 시도했습니다.

하지만 실제 알약 각인은 일반 OCR 데이터와 달리 다음과 같은 특성이 있어 인식률이 매우 낮았습니다.

|문제 요인|설명|
|-|-|
|낮은 대비|알약 표면과 각인 색이 거의 같음|
|음각/양각|글자가 인쇄된 것이 아니라 눌리거나 튀어나온 형태|
|곡면|알약 표면이 평면이 아님|
|반사/흐림|촬영 조명에 따라 각인이 사라짐|
|작은 글자|알약 crop 안에서도 각인 영역이 매우 작음|
|회전|알약 방향이 일정하지 않음|

특히 단순 오인식보다 더 큰 문제는 **문자 일부가 누락되는 경우**였습니다.

```text
복원 가능성이 있는 경우:
OCU → 0CU, OCV

복원이 어려운 경우:
OCU → OU
OCU → 빈 값
OCU → 전혀 다른 문자열
```

`OCU → 0CU`처럼 비슷하게 틀리는 경우는 API fuzzy matching으로 복원할 수 있지만, `OCU → OU`처럼 특정 글자가 아예 빠지면 후보 복원이 매우 어렵습니다.

따라서 EasyOCR은 현재 데이터에서는 **보조 검증 신호로도 신뢰하기 어려운 수준**으로 판단했습니다.

## 3\. EasyOCR 전처리 및 OCR rescue 강화 시도

EasyOCR의 인식률을 개선하기 위해 전처리와 회전 OCR을 늘리는 방식도 실험했습니다.

적용한 방식은 다음과 같습니다.

```text
알약 crop
→ 확대
→ CLAHE
→ sharpening
→ threshold / 반전
→ 0, 90, 180, 270, ±30, ±45도 회전 OCR
→ OCR 후보군 생성
→ API 각인 정보와 fuzzy matching
```

하지만 이 방식은 두 가지 문제가 있었습니다.

첫째, 처리 시간이 너무 길어졌습니다.  
보조 검증 단계가 약 4\~5분 정도 걸려 웹 데모에 사용하기 어렵다고 판단했습니다.

둘째, 근본적인 인식률 문제는 해결되지 않았습니다.  
전처리와 회전을 많이 적용해도 각인 자체를 누락하는 문제는 계속 발생했습니다.

따라서 OCR rescue 강화 버전은 **메인 웹 로직에 적용하지 않는 것이 낫다**고 판단했습니다.

## 4\. 각인 라벨 구축

EasyOCR 대신 사전학습 OCR 모델을 fine-tuning하기 위해 각인 문자열 라벨을 구축했습니다.

기본 베이스는 기존 CNN/RTMDet 학습에 사용한 메타데이터 CSV인 `merged\_train\_after\_category\_merge.csv`를 사용했습니다. 이 파일에는 다음 정보가 포함되어 있었습니다.

```text
final\_class\_idx\_merged
dl\_name
print\_front
print\_back
drug\_shape
color\_class1
color\_class2
```

이후 낱알식별정보 API를 이용해 각인 정보를 보완 및 검증했습니다.

진행 결과는 다음과 같습니다.

|항목|결과|
|-|-:|
|전체 클래스 수|118개|
|base CSV에서 각인 보유 클래스|115개|
|API 비교 후 검토 필요 클래스|7개|
|OCR synthetic 학습용 라벨 row|146개|

검토 대상 중 일부는 API가 다른 제조사나 다른 용량의 약품을 잡는 문제가 있었습니다.  
예를 들어 `토비애즈서방정 4mg`을 검색했을 때 API가 `토비애즈서방정 8mg`을 잡는 문제가 있어, 검색어 생성에 `mg → 밀리그램 / 밀리그람` 변환과 용량 필터링을 추가했습니다.

라벨 정제도 수행했습니다.

|원본 라벨|정제 후|
|-|-|
|`I분할선Y`|`IY`|
|`2분할선0`|`20`|
|`마크 PGN 150`|`PGN 150`|
|`마크`|텍스트 OCR 학습 대상에서 제외|

정제 후 `ocr\_text\_labels\_clean\_for\_synthetic.csv`를 생성했습니다.

## 5\. TrOCR 사전학습 모델 fine-tuning 1차 실험

EasyOCR의 한계가 커서 Hugging Face의 사전학습 OCR 모델인 `microsoft/trocr-small-printed`를 사용했습니다.

첫 번째 실험은 각인 문자열이 비교적 크게 보이는 text-line 스타일 synthetic 데이터로 진행했습니다.

데이터 생성 결과는 다음과 같습니다.

|항목|결과|
|-|-:|
|raw label rows|146개|
|unique imprint texts|173개|
|train 이미지|11,764장|
|val 이미지|2,076장|

TrOCR 학습은 정상적으로 진행되었고, 초기 로그에서 loss가 빠르게 감소했습니다.  
처음에는 `generation\_config` 저장 방식 문제로 checkpoint 저장 오류가 발생했으나, `model.config`에 들어간 generation parameter를 `model.generation\_config`로 옮겨 저장 오류를 해결했습니다.

학습된 모델을 기존 CNN crop 이미지에 테스트한 결과는 좋지 않았습니다.

|항목|결과|
|-|-:|
|테스트 이미지 수|300장|
|정답 각인과 정확 일치|4장|
|부분 포함까지 허용|약 10장|
|평균 문자열 유사도|낮음|

특정 문자열을 반복 출력하는 현상도 나타났습니다.

```text
K50
A-008
V100
D5
G40
ZLT-100
```

즉, 실제 각인을 읽는다기보다 synthetic 학습 데이터에서 본 특정 문자열을 hallucination처럼 생성하는 경향이 있었습니다.

## 6\. TrOCR fine-tuning 2차 실험: 알약 전체 crop 스타일 synthetic

1차 실험의 문제는 학습 데이터와 실제 테스트 데이터의 형태가 다르다는 점이었습니다.

```text
1차 학습 데이터:
각인 문자열이 크게 보이는 text-line 이미지

실제 테스트 데이터:
알약 전체 crop 안에 작은 각인이 있음
```

그래서 2차 실험에서는 알약 전체 crop과 비슷한 synthetic 데이터를 새로 만들었습니다.

적용한 생성 방식은 다음과 같습니다.

|항목|내용|
|-|-|
|알약 형태|원형, 타원형, 캡슐형, 둥근 사각형|
|이미지 크기|160\~256px 랜덤|
|각인 위치|중앙, 상단, 하단, 좌우 약간 이동|
|각인 크기|실제 crop처럼 작게 배치|
|색상/대비|저대비 각인|
|질감|음각/양각 느낌의 shadow 적용|
|조명|gradient, highlight 적용|
|기타|회전, blur, noise, 분할선 추가|

생성 결과는 다음과 같습니다.

|항목|결과|
|-|-:|
|unique imprint texts|129개|
|train 이미지|10,965장|
|val 이미지|1,935장|
|총 이미지|12,900장|

이 데이터로 TrOCR를 3 epoch 재학습했습니다.

|항목|결과|
|-|-:|
|epoch|3|
|최종 eval\_loss|0.05843|
|train\_loss|0.4952|
|학습 시간|약 14분|
|저장 모델|`trocr\_pill\_rec\_pillstyle\_best`|

학습 loss만 보면 synthetic 데이터에는 잘 적응한 것으로 보였습니다.

## 7\. 실제 crop 테스트 결과

하지만 2차 모델도 실제 CNN crop 이미지에 적용했을 때 성능이 크게 개선되지 않았습니다.

결과 요약은 다음과 같습니다.

|항목|결과|
|-|-:|
|테스트 이미지 수|300장|
|정답 각인과 정확 일치|4장|
|부분 포함 허용|약 9장|
|유사도 0.7 이상|약 4장|
|평균 문자열 유사도|약 0.17|

반복 출력 문제도 계속 남아 있었습니다.

|반복 예측 문자열|빈도|
|-|-:|
|`K50`|87회|
|`A-008`|26회|
|`V100`|19회|
|`D5`|12회|
|`G40`|12회|
|`ZLT-100`|11회|

따라서 pill-style synthetic으로 학습 데이터를 실제 crop 형태에 가깝게 바꾸었음에도, 실제 알약 crop에서는 각인을 안정적으로 읽지 못했습니다.

## 8\. 현재 결론

현재까지의 실험 결론은 다음과 같습니다.

```text
EasyOCR:
알약 각인 인식률이 매우 낮아 사용 어려움

전처리/회전 강화 EasyOCR:
속도만 크게 느려지고 근본 개선은 부족함

TrOCR + text-line synthetic:
synthetic에는 적응하지만 실제 알약 crop에서는 반복 문자열 생성 문제가 있음

TrOCR + pill-style synthetic:
학습 loss는 낮아졌지만 실제 crop 성능은 크게 개선되지 않음
```

가장 큰 원인은 **Text Recognizer와 입력 데이터 형태의 불일치**로 보입니다.

TrOCR는 기본적으로 문자열 영역이 어느 정도 잘려 들어오는 recognizer에 가깝습니다.  
하지만 현재 테스트 입력은 각인 영역 crop이 아니라 **알약 전체 crop**입니다.

즉 현재 구조는 다음 문제가 있습니다.

```text
모델이 필요한 입력:
각인 영역 crop

현재 넣고 있는 입력:
알약 전체 crop
```

알약 전체 crop 안에서는 각인 영역이 너무 작고, 위치도 일정하지 않으며, 저대비/음각/반사 문제까지 있어 recognizer가 안정적으로 읽기 어렵습니다.

## 9\. 향후 방향

현재 단계에서 OCR을 웹 데모의 최종 판단에 강하게 반영하는 것은 위험합니다.

### 9-1. 단기 방향

```text
웹 메인 로직에서는 OCR 의존도 낮춤
RTMDet + CNN + API 메타데이터 중심으로 유지
OCR 결과는 참고/디버그용으로만 표시
```

### 9-2. 중기 방향

OCR을 계속 살리고 싶다면 synthetic 데이터만으로는 부족합니다.

필요한 데이터는 다음 중 하나입니다.

|방식|필요 데이터|
|-|-|
|Text Recognizer 개선|실제 각인 영역 crop + 문자열 라벨|
|Text Detector 개선|알약 crop + 각인 bbox/polygon 라벨|
|약한 라벨 방식|알약 crop + 각인 문자열 라벨, 단 성능 제한 있음|

현실적인 최소 실험은 다음 정도입니다.

```text
문제 클래스 20\~30개 선정
각 클래스당 실제 각인 crop 5장 정도 수작업 생성
총 100\~150장 실제 각인 crop 확보
synthetic 데이터와 섞어서 TrOCR 추가 fine-tuning
```

또는 전체 클래스 기준으로 최소 검증하려면 다음 정도가 필요합니다.

```text
118개 클래스 × 각 3장 = 약 354장
```

## 10\. 최종 공유용 결론

현재 OCR 실험 결과만 놓고 보면, **알약 각인 인식은 기존 EasyOCR이나 synthetic-only TrOCR 방식으로는 실사용 수준에 도달하지 못했습니다.**

특히 문제의 핵심은 모델 자체보다도 **각인 영역 추출 부재**입니다.  
알약 전체 crop을 그대로 OCR recognizer에 넣으면, 각인이 너무 작고 저대비라서 모델이 실제 각인을 읽기보다 학습된 문자열을 반복 생성하는 경향이 나타났습니다.

따라서 현재 웹 데모에서는 OCR을 최종 후보 결정 로직에 강하게 반영하지 않고, **RTMDet + CNN + API 메타데이터 기반 판단을 중심으로 유지하는 것이 안전합니다.**

OCR을 계속 개선하려면 다음 단계는 사전학습 모델 변경이 아니라 **실제 각인 영역 crop 또는 각인 bbox 라벨을 소량이라도 구축하는 것**이 필요합니다.
